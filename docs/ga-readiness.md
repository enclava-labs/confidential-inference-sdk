# General-availability readiness ledger

Ledger of gaps found while integrating the SDK with a production OpenAI-style
inference consumer. Each entry names the evidence, the consumer-facing impact,
and the resolution status. Entries move to **Resolved** only with a passing
test or live run named in the row.

Integrator requirements: OpenAI `models`, Chat Completions with streaming,
tool calls and image input, embeddings, and the Responses API (create,
retrieve, cancel, delete, input items, input token counting, compaction,
streaming); per-tenant credentials; caller cancellation; exact usage for
billing; customer-local (private-origin) and confidential (attested)
endpoints behind one client.

| GA-08 | NEAR live | Re-probed 2026-10-20: model-direct host `gpt-oss-120b.completions.near.ai` still resets the TLS handshake while `cloud-api.near.ai` (same IP) serves `/v1/models` (59 models). Re-probed 2026-11-02 (twice): the model-direct host still fails the TLS handshake (`curl` exit 35, `UNEXPECTED_EOF`). The gateway returns fresh gateway and model TDX quotes, GPU evidence, and a quote-bound gateway TLS fingerprint, but NEAR documents that model instances with different measured configurations share one model signing key ([model attestations](https://docs.near.ai/cloud/verification/cloud-api/model-attestations.md)), and the gateway does not bind its upstream endpoint to the model quote. Gateway TLS plus model E2EE therefore cannot tie inference to a pinned model measurement; unlike RedPill's ACI sessions (GA-22) there is no per-instance binding to enforce. Also open before any NEAR route returns: `near_live_tee_measurement` does not pin the dstack key-provider (KMS root) event, so a host-chosen KMS could derive the attested TLS key (the gap fixed for RedPill in GA-22). | NEAR route unusable until NEAR exposes a per-instance binding (or the model-direct endpoint returns) and the verifier pins the KMS; retargeting the current verifier would weaken its TLS binding. |
| GA-09 | Go binding distribution | `bindings/go` is committed but its module path is unpublished; consumers need a `replace` directive plus a separately built shared library. Concrete consequence: a consumer Dockerfile cannot `go mod download` a module with a `replace` pointing outside its build context, and an `alpine` (musl) runtime cannot load a glibc-built FFI library. Release tooling already covers the Rust side (`check_release_packaging.py` lists 7 publishable crates incl. `confidential-inference-trust-cli`; `generate_release_manifest.py`, `generate_sbom.py`). Plan: (1) tag `bindings/go` as a submodule tag (`bindings/go/vX.Y.Z`) so consumers drop the `replace`; (2) attach per-target `libconfidential_inference_ffi` artifacts (linux-gnu amd64/arm64, linux-musl amd64/arm64, darwin arm64) with SHA-256s to the release manifest and SBOM; (3) consumers pin the library hash and set `CONFIDENTIAL_INFERENCE_FFI_LIBRARY` (or `WithLibraryPath`); (4) **done:** FFI status JSON carries `abi_version` (`CONFIDENTIAL_INFERENCE_FFI_ABI_VERSION = 1`, header `#define`), and Go/Python/Node refuse a missing or mismatched version at load with `abi_version_mismatch` (`status_json_reports_abi_version`, Go `TestValidateABIVersion`, Python `test_abi_version_validation_rejects_mismatch`, Node `ABI version validation rejects mismatches`). Remaining owner actions (1)-(3): tag/publish — blocked by the existing release checklist (no tag yet, no signed live-conformance report). | No reproducible consumer or container build until a tagged module + library artifacts exist. |
